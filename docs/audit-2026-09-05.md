# Repository audit — 5 September 2026

This pass covers correctness, engine performance, storage/offline behavior, browser workflows, and the product gap between casual analysis and professional preparation. It follows the three earlier September audits. Changes are local commits on `main`; nothing was pushed or deployed.

## Scope and evidence

Reviewed the application orchestration, engine hooks and UCI pipeline, review pool, PGN/tree handling, analysis scoring, game/clock behavior, library and recovery storage, remote data boundaries, service worker, component styles, tests, package configuration, and CI/deployment workflows. The source tree contains 224 tracked files, including tests. This is an application audit, not an assertion that every generated engine byte or dependency implementation was inspected, or that no bugs remain.

Evidence is separated below into reproduced defects, measured performance, code findings needing additional reproduction, and proposed features. Automated UI regressions use scripted UCI responses and local HTTP fixtures. Real Stockfish WASM was separately exercised for the benchmark and final desktop/mobile screenshots.

## Largest measured performance gain

Single-thread Stockfish profiles now use up to four independent engines for sufficiently long desktop reviews. This works without cross-origin isolation. Mobile, low-core, reported low-memory (4 GB or less), small-hash, and short-queue cases retain one engine. Hash is divided across workers; WASM heaps and network weights are still additional per-worker memory costs.

Real Chromium/WASM benchmark: 18 reported logical cores, Stockfish 18 Lite single-thread local profile, 33 nonterminal Opera Game positions, depth 18, 64 MB total hash, fresh workers, ABBA ordering.

| Run | Workers | Wall time | Nodes | Completed positions |
| --- | ---: | ---: | ---: | ---: |
| A1 | 1 | 15.493 s | 28,385,507 | 33 |
| B1 | 4 | 7.348 s | 23,194,688 | 33 |
| B2 | 4 | 7.744 s | 23,194,688 | 33 |
| A2 | 1 | 16.220 s | 28,385,507 | 33 |

Mean wall time fell from 15.857 s to 7.546 s: **2.10× faster, about 52% less time**. This is a particular game/device/profile result, not a universal speedup or a measurement of the already-pooled multithread profile. Partitioned hash histories change search work, as the node counts show; equal depth does not imply identical searches or equal playing strength.

Reproduce with `npm run dev -- --host 127.0.0.1 --port 4324`, then `node scripts/benchmark-review-browser.cjs`. The benchmark fails if any position does not complete.

A proposed library parsing optimization was rejected after measuring it: two normalization passes over 500 games totaling about 6 MB of PGN took a median 2.015 ms across seven runs. It does not justify complexity. IndexedDB transaction/write costs were not included in that measurement.

Final build: application entry 91.95 kB gzip, React chunk 60.35 kB, chess/board chunk 37.31 kB; ECO remains a separate 61.18 kB lazy chunk. These figures exclude engine assets. Full Stockfish downloads remain much larger than Lite, so making Full the default would work against beginner/mobile startup.

## Remaining correctness and reliability priorities

These are code findings or validation gaps, not claims of browser reproductions performed in this pass.

1. **Surface autosave failures.** `src/App.tsx` ignores the result of `writeAutoSavedGame`. `src/engine/autoSave.ts` returns `failed` on unavailable/quota-limited storage and `too-large` above 2 MB; oversized saves remove the old recovery slot. The user needs a persistent recovery-status warning and a PGN export action. Verify quota denial and oversized variation trees before shipping that change.
2. **Define the review CPU budget explicitly.** `planReviewPool` receives profile, capabilities, queue size and hash, but no user-selected Threads limit. Its automatic pool budget can differ from the setting used for an individual search. Professional users need a clear total review budget, with tests asserting the aggregate worker/thread limit.
3. **Make browser QA a deployment dependency.** The Pages deployment workflow audits, lints, runs unit tests and builds, but does not gate deployment on completion of browser QA. An independent CI failure can otherwise coexist with a successful deployment.
4. **Audit cached evaluation identity.** The position evaluation map uses FEN, while repetition history and engine/profile provenance can matter. Before changing cache semantics, reproduce identical-FEN/different-history cases and define when imported/cloud/local scores may replace each other.
5. **Test browser-specific failure modes.** This pass uses Chromium. Firefox/WebKit, touch-only annotation controls, storage denial, and a worker that never finishes initialization need dedicated coverage. The pool has a boot timeout; verify consistent recovery behavior in each live-engine path.

## UI/UX assessment

The board remains the dominant surface on desktop and fits the 375px mobile viewport. Desktop exposes graphs, library and analysis together; mobile protects board size by putting analysis below it. The expanded move-entry form has no horizontal overflow, retains typing focus, explains illegal notation and provides a touch-sized input. Coach remains the default approachable reading; Pro exposes detailed lines and engine controls.

The original Coach/graph disagreement was a trust problem, not merely formatting. The revised view separates the position reading from the local candidate line and labels its depth. Percentages still need careful teaching: the app's score-derived “win chance” and Stockfish's WDL distribution are different models, not a personalized prediction for the human at the board.

Recommended next UI work:

- **Beginner:** a short first-analysis explanation of whose score is shown, what depth means, and why “best” can change; an example-driven import/review flow; an obvious recovery/export status.
- **Mobile:** label or briefly explain icon-only top actions, and provide a discoverable touch alternative for arrows/marks. Keep advanced controls below the board and test internal panel scrolling, not only page overflow.
- **Professional:** a compact analysis source/budget strip, richer study navigation, keyboard shortcut discovery, and explicit feedback about what was saved. Keep raw UCI controls in Engine Lab.
- **Accessibility:** keyboard move entry improves access but is not a substitute for a screen-reader playthrough. Test board announcements, variations, promotions, dialogs, and engine updates with assistive technology.

## Features that would most improve professional coverage

Existing strengths include MultiPV, infinite search, selected-move search, non-mutating PV preview, variation PGN import/export, tablebases, opening exploration, drills, review navigation, and a local library. Building duplicates of those would add little.

| Priority | Feature | Acceptance target |
| --- | --- | --- |
| 1 | Repertoire studies and spaced repetition | Named chapters, training side, due positions, transposition-aware progress, and lossless annotated PGN export. Beginners get “practice today's moves”; experts retain the full tree. |
| 2 | Database position search | Exact position first, then material/partial-position filters; search large libraries off the UI thread; result links preserve the matching move. |
| 3 | Study annotations and time usage | Searchable notes/tags, move-time graph from clock metadata, chapter navigation and stable local persistence. |
| 4 | Multi-engine comparison | Clearly separated engine/profile/depth provenance and explicit resource limits; consider an optional local UCI bridge rather than implying browser WASM can run arbitrary binaries. |
| 5 | Chess960 and tournament rules | Audit castling, notation, FEN, engine options and imports together. Distinguish claimable draws from automatic endings if tournament-rule play becomes a product goal. |

This pass improves the foundation; it does not make the app a complete professional database/repertoire suite.

## Research and resulting decisions

- [Stockfish UCI protocol](https://official-stockfish.github.io/docs/stockfish-wiki/UCI-Protocol-and-Stockfish-Commands.html): score bounds are inequalities, not exact evaluations. This supports the pooled-score fix and the need for clear search provenance.
- [Stockfish FAQ](https://official-stockfish.github.io/docs/stockfish-wiki/Stockfish-FAQ.html): MultiPV trades top-line search strength for alternatives; thread/hash choices depend on the workload. Keep simple defaults and explicit professional resource controls rather than maximizing everything.
- [nmrugg/stockfish.js](https://github.com/nmrugg/stockfish.js): the current browser package offers large/full and smaller/weaker Lite builds. Single-thread builds cannot themselves use multiple threads; independent instances can still analyze separate positions concurrently.
- [lichess-org/stockfish-web](https://github.com/lichess-org/stockfish-web): specialized for Lichess integration and points general integrations toward Stockfish.js. There is no evidence here that changing engine repositories is a better first investment than fixing scheduling and provenance.
- [rooklift/nibbler](https://github.com/rooklift/nibbler): useful reference for continuous analysis, selected-move search, PV inspection and Chess960. Several of these workflows already exist here.
- [En Croissant](https://github.com/franciscoBSalgueiro/en-croissant): useful reference for repertoire repetition, database/engine management and position search. These identify substantive professional gaps beyond adding more engine switches.

External repositories were used as documented workflow references; their implementations were not exhaustively audited or copied into this project.
