What this pass found, what it changed, and what it did not. Twenty-five commits

Claims here are marked **measured** or **reasoned**. That distinction cost real
time to get right during the work and is worth keeping in the record.

## The biggest performance win: review on several engines

**Measured.** A 116-move game review at depth 16 went from **105.5s to 21.0s**
— roughly 5×.

The lever was not what I first assumed. Three ablations established that React
rendering was *not* the bottleneck: each one moved main-thread cost by under 2%,
and the UCI message handler totalled 13ms across 1596 calls (0.1%). The cost was
the engine searching — 47.8s of a 105.5s review — one position at a time on one
worker.

Positions in a review are independent, so the wall clock was a scheduling choice
rather than a fact about the work. `reviewPool.ts` sizes a pool from the device's
actual capabilities and `reviewPoolRunner.ts` runs it. Grades came out within 0.3
accuracy points of the single-engine run — less than the variance between two
single-engine runs of the same game.

The sizing divides rather than multiplies. Each engine owns a transposition
table, and adjacent positions transpose heavily, so N engines give up most of
that reuse; total hash and threads are split so the reader gets the memory and
CPU they asked for, not N times it. A queue under 12 positions never earns back
the ~1s each WASM boot costs, and a phone gets one engine.

**Verified in the real app, not just the harness:** loading a 120-position
classical game and starting a review spun up 4 workers and reached 118/120 in
~5.8s with actual Stockfish.

## The second win: a 61 kB table out of the boot path

**Measured.** `eco.json` — the largest asset after the engine — was fetched
**106ms into boot**, on an empty board, for anyone whose last session was in
analysis mode.

Two hooks read that table and share one lazily-loaded promise. One gate waited
carefully for a move to exist; the sibling beside it opened on `engineEnabled`
alone, which is true at boot for the app's most common user. Whichever gate opens
first pulls the table for both, so the careful one was decorative.

The fix could not simply copy the other gate's condition: a review reads the line
forward from the root, not the path the user has navigated, and at the root of an
imported game that path is length 1 while the game is complete. It waits on the
tree holding a move instead.

## Bugs

Ordered by what they would have cost a user.

**Library games could vanish.** `indexedDbFailed` is session state, so a browser
that refuses IndexedDB one session and allows it the next is ordinary — quota
pressure, a blocked upgrade, an eviction. The next session read an IndexedDB that
never received the write, returned an emptier library than the user saved, and
left the real snapshot unread in localStorage. Silent, and after the app had said
"Saved to the library." A successful load now rescues a newer stranded snapshot
and releases it. It compares `updatedAt` rather than assuming the fallback is
newer, so a snapshot that fails to clear cannot shadow later saves.

**A dying pooled engine stalled the whole review.** A worker that died recorded
its failure and stopped there. Nothing matches a predicate after that, so a wait
already parked sat until its own timeout — 20s for a boot, 60s for a `bestmove` —
before the caller could fall back. A pool that stalls a minute before admitting
it is broken is slower than the single engine it replaced. Cancellation had the
same shape and held `done` for a further 60s on unmount.

**Nine contrast defects**, the last three found by the gate rather than by hand.
See below.

**A Threads value the reader chose was overridden** on every `readyok`, because
the comparison re-sent the recommendation whenever it differed from the applied
value rather than only when nothing had been applied.

**The Coach card named a move and denied having one** — it could print a best
move and, in the same breath, ask you to start an analysis to get a candidate
line.

**A move note swallowed a space you typed**, because the field rendered the
normalized value rather than the draft.

**The review's fallback never resumed.** Handing work back to the single engine
re-queued it without re-entering the effect that drains the queue.

**A review starting while one ran doubled it** rather than replacing it.

**Hash was sized to the device only after a first visit**, so the first run got a
default that ignored the machine.

**The mode you chose scrolled off screen on a landscape phone.**

## UI/UX

A contrast gate now runs in the browser suite: **22 sweeps**, both themes, across
analyze, review, new game, PGN export, library and play, at desktop, mobile and
landscape sizes — 0 under the floor.

Building the probe was most of the work, and three of its own bugs are worth
recording because each produced confident nonsense:

- Compositing forced alpha to 1 after one layer, reading a teal pill on black as
  near-white — 38 false failures at 1.69:1.
- Skipping gradients silently measured 16 elements; caught only because the probe
  asserts a minimum count.
- Measuring a gradient-filled control by stepping past it read 1.01:1. A filled
  control is measured against its worst stop.

Also fixed: selecting a time control dimmed its own description; the mistake
stepper's buttons had no real touch target; the graph cursor was invisible on the
light theme; a copied game link had no fallback when the clipboard refused it.

**Keyboard focus was audited and is sound** — no defect. The global ring computes
to `(0,3,0)`, outranking the `outline: none` at `(0,2,1)` on engine settings; no
portals, so dialogs stay inside `.app-shell`; every Tab-reachable element carries
a role in the ring's selector list; `.mtree-scroll` is `tabIndex={-1}`, so its
bare `outline: none` is correct.

## New features

**Step from one mistake to the next.** Critical Moments ranks the five costliest
and everything past the fifth was reachable only by scrolling for a coloured dot.
The stepper reads the *filtered* rows, so narrowing to Black's middlegame steps
Black's middlegame mistakes. It appears only when there are faults, states its
position ("Mistake 3 of 3"), explains its disabled state rather than greying out,
and puts the board *before* the mistake so the reader has to find the better move
themselves.

## What I did not do, and why

**Publishing this.** Outward-facing, so it waits on you.

**Pushing.** 25 commits sit on local `main` with no PR. You authorized committing
in small steps, not publishing.

**Freezing review verdicts.** The fault set updates as you browse: stepping back
through mistakes, the counter went "3 of 3" → "2 of 3" → "2 of 4", and the
tallies moved from `Inaccuracy 1 / Mistake 1 / Blunder 1` to
`Inaccuracy 0 / Mistake 2 / Blunder 2`. It is stable when idle — visiting a
position makes the shared engine analyse it deeper, which reclassifies the move.
Navigation is sound (it steps by ply, not index, so nothing is skipped or
repeated), so this is not a correctness bug. But a "Game Review" reads as a
report, and reports whose numbers move while you read them feel broken. Freezing
at review time versus letting them improve is a question about what a review *is*.

## A correction on coverage

I twice described `useGameTree.ts` at 0% as the worst gap in the codebase, "the
app's core data structure untested." That was misleading, and the record should
say so.

The tricky tree surgery — `promoteToMainLine`, `removeSubtree`, `variationRootId`
and three more — already lives in `src/engine/moveTree.ts` with 24 tests. All
eight pure functions in `useStockfishEngine.ts` are likewise extracted *and*
tested. What is uncovered in both files is React and worker lifecycle wiring,
which this repo deliberately covers through the browser harness instead. The
residual risk is much lower than the raw percentage suggested.

Coverage was still worth measuring: it pointed directly at the two real bugs
above. `reviewPoolRunner.ts` sat at 15.78% and `gameLibraryStorage.ts` at 48%,
and in both the untested half held the defect. The number is a pointer, not a
verdict.

## Method

Every fix has a test that fails without it. Where the failure mode is a stall
rather than a wrong answer, the tests keep real timers and assert immediately, so
a regression shows up as the suite hanging rather than as a pass — the three
pooled-engine tests run in 123ms and time out without the fix.

Two claims in this document rest on reading code rather than measurement, and are
labelled where they appear. One earlier claim was withdrawn during the work: a
mutation test on the review fallback showed no difference, because `Promise.all`
rejects at engine construction before survivors answer, making partial-boot and
total-boot failure indistinguishable. It is reported as reasoned, not measured.

`npm run verify`: 1219 passed, 1 skipped, 93 files. Browser suite: green.
