### Saved evaluation identity

The optional `[%wcengine ...]` PGN command contains a URI-encoded JSON array:
`[profile, packageBuild, uciEngineName]`. It accompanies `[%eval]`; disabling
engine annotations removes both. Unknown or malformed identity metadata does
not invalidate the score. Older PGNs explicitly say their engine is unrecorded.
The local build comes from `localStockfishBuild.json`, which the asset sync
script updates after copying the actual engine files; installing a newer npm
package alone must not relabel the already bundled files.

The live position map still prefers deeper readings, including across producers,
and displays their identity. Game reviews now keep a separate map for each run:
only sufficiently deep, exact readings from the selected producer can be reused.
Unrecorded PGN/cloud sources and other engine builds do not silently fill a run.
Completed and stopped reports retain their own readings; stopped runs indicate
whether positions remain. The review graphs use that same map.

### Refreshing and exporting a review

Pro's **Fresh review** searches every position again, ignoring prior position
readings and the previous report. It does not promise cold engine hash tables
or identical results across machines. A normal repeat can reuse the preceding
report even when the board retains deeper scores from another engine.

**Export review** downloads the selected branch as a standalone PGN, including
its report's scores, engine identity, comments and clocks. Headers record target
depth, total hash budget, completion status and the number of reused positions.
Partial exports contain only known readings. Normal PGN export continues to
describe the current study and its live evaluations.

Reports remain in memory until Pro's **Save review** is selected. A saved run
retains its full reviewed branch, annotations, exact engine readings (including
WDL), settings, timestamps and completion status. **Saved reviews** can reopen a
run from another game; when the current line matches, it replaces only the
report. The match uses the full root FEN and UCI history, independent of node IDs.

Storage permits 50 runs, with a 512 KB / 2,048-ply limit per run. It never evicts
an older run to make room. Counts and inserts share an IndexedDB transaction,
which serializes simultaneous saves from different tabs. The UI reports success
after transaction completion, consistent with
[MDN's transaction guidance](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/complete_event).
An unavailable or full browser store reports a failure while preserving the
open report and its PGN export. Metadata is listed without replaying every PGN;
opening a selected run validates its schema, line and readings.

**Compare with open review** requires the same root and complete move history.
The comparison leaves both maps intact, gives both engine identities and limits,
and lists positions in move order. Positive scores and changes favor White;
changes are open minus saved, in pawns. Mate scores retain their signed distance
and do not produce a fabricated pawn delta. Missing readings stay missing.
Known checkmates and drawn FENs are omitted from engine-position counts, as they
are in review planning. Ten positions are rendered initially, with more available
on request; selecting one reveals the board on a phone.

These records are local to the browser and separate from the game library.
**Export review backup** now downloads all saved runs as a version-1
`web-chess-review-backup` JSON archive. It retains complete and partial reports,
PGN annotations, source identities, settings, WDL, search telemetry and run
timestamps. Ordinary review PGN remains useful for sharing an annotated line.

**Import review backup** reads UTF-8 JSON and validates every record before any
write. An oversized file, malformed encoding or invalid second record rejects
the whole batch. The archive limit is 50 × 512 KiB plus 4 KiB for its envelope;
each record also retains the existing 2,048-ply limit. A dedicated worker handles
file reading, JSON parsing and PGN replay so those operations do not block board
input. The production worker is fetched on demand (59.52 kB uncompressed in this
build), not on initial page load.

Import compares normalized record content, ignoring IDs and evaluation-array
order when detecting an identical run. Different scores, notes, settings or
timestamps remain distinct. An ID conflict gets a new identifier; existing
records are never overwritten or evicted. All additions must fit in the 50-run
store or none are added. Checking current contents and inserting the batch use
one readwrite transaction, serializing competing imports from other tabs. The
success notice waits for transaction completion. These choices follow
[IndexedDB transaction semantics](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction)
and insert-only [object-store add](https://developer.mozilla.org/en-US/docs/Web/API/IDBObjectStore/add).

Import refreshes Saved reviews without opening a different board or report.
Choose a run explicitly to use it. A timeout or lost worker response asks the
user to check saved reviews and retry; content deduplication makes a repeated
import safe. Export stops if a stored record is unreadable instead of silently
omitting it from the archive.

### Enlarged text and usable reading space

At 1280×812 and 200% root text, the analysis header occupied 327px of the 472px
workspace, leaving 145px for content. It now stays pinned only while occupying
at most 35% of the workspace height. Otherwise it scrolls away, making the full
panel viewport available for reading. One desktop scroll container preserves
the reading position when the header changes between these modes. Native focus
scrolling and the Opening Intel shortcut account for the pinned header through
[scroll padding](https://developer.mozilla.org/en-US/docs/Web/CSS/scroll-padding-top).

The board's dimension calculation also used a stale root font size when only
text changed. A hidden one-rem box now triggers the existing resize calculation
through [ResizeObserver](https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver).
This box is independent of board dimensions, avoiding a resize feedback loop.
On a short desktop, a wrapped footer can still leave less room than the minimum
board needs. The board stage now scrolls and keeps both its top and bottom
reachable instead of clipping them. Normal-size boards remain centered.

Checks change text from 100% to 200% and back without a window resize, verify
board resizing, keyboard access to both back ranks, visible review-button
focus, and the opening shortcut. This follows the intent of W3C's
[Resize Text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html) and
[Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) guidance. A chess
board's two-dimensional nature does not excuse clipped surrounding controls.
These synthetic checks are not a complete WCAG conformance assessment or a
substitute for physical-device testing.

### Returning visits

The immutable-asset change removes four network requests from the tested warm
startup. This is a request count, **not** a claimed percentage improvement in
page-load time. The document, engine assets and any previously unseen chunks may
still need the network. The cache check deliberately disables the HTTP cache so
that the browser's own freshness heuristics cannot account for the improvement.

The policy is limited to hashed JS/CSS beneath this service worker's `assets/`
path. A Range request still reaches the network and returns 206. Offline loads
retain the isolation headers needed for multithreaded Stockfish.

## Stockfish and reference-repository research

- [Stockfish 19](https://stockfishchess.org/blog/2026/stockfish-19/) was released
  on September 5. It adds native WebAssembly targets and stricter position/UCI
  validation; invalid input can terminate the engine. A migration needs explicit
  handling and tests for this failure mode.
- The app's provider,
  [nmrugg/stockfish.js](https://github.com/nmrugg/stockfish.js), still documents
  Stockfish 18. On this date `npm view stockfish version` returned `18.0.8`; the
  app's full CDN URLs pin `18.0.7`. The local lite build and the full browser build
  are different strength/download choices. The full build exceeds 100MB; making
  it every beginner's default would impose a substantial download.
- [lichess-org/stockfish-web](https://github.com/lichess-org/stockfish-web)
  includes SF19 and SF19 small-network builds, but explicitly describes its
  integration as more involved. It is an adapter/build migration, not a safe
  substitution of a version number in the current worker URLs.
- [Lichess's evaluation controller](https://github.com/lichess-org/lila/blob/master/ui/lib/src/ceval/ctrl.ts)
  throttles updates, reuses completed search effort, and unloads a worker when
  another tab starts analysis. This app already batches engine updates and
  caches finite navigation searches. Cross-tab resource ownership is a useful
  next comparison, with care to preserve intentionally running game reviews.
- [Nibbler](https://github.com/rooklift/nibbler) exposes constrained root searches,
  PV previews, arbitrary variations and Chess960. This app already has the first
  three. Chess960 remains a rules/PGN/board/engine project, not a missing switch.
- [Stockfish's UCI documentation](https://official-stockfish.github.io/docs/stockfish-wiki/UCI-Protocol-and-Stockfish-Commands.html)
  defines `searchmoves` as a restriction on root moves. Its resulting score is
  conditional on that restriction, which is why it must not overwrite a
  whole-position reading. The same documentation recommends MultiPV 1 for the
  best performance; game review already uses one PV per worker.
- [Lichess's accuracy explanation](https://lichess.org/page/accuracy) defines
  the centipawn-to-Win% curve used here and describes a human-game benchmark.
  [Stockfish's WDL option](https://official-stockfish.github.io/docs/stockfish-wiki/UCI-Protocol-and-Stockfish-Commands.html#uci-showwdl)
  models engine self-play outcomes. These are different estimates even when
  they use the same position and engine evaluation. The existing beginner
  Analyze guide already explains this distinction; `dfa48c4` adds guidance
  beside the charts, including Review and Pro. The accuracy model stays distinct
  from WDL.
- [Vite's production guidance](https://vite.dev/guide/build.html) describes old
  dynamic-import filenames disappearing after deployments. The cache and dialog
  fixes above address the cached and uncached cases separately.

Decision: keep the working SF18 browser integration for now. Evaluate the 18.0.8
provider patch separately; prototype SF19 behind a distinct engine adapter and
compare download, boot time, search throughput, memory and position validity
before changing the default.

## Features worth building next

1. **Repertoire study with a due queue.** Build on the existing saved variation
   trees and line drills: chapter names, side to train, remembered attempts,
   due dates, and a short daily session. Keep imports/exports lossless. Useful
   both to a beginner learning one opening and to a tournament player reviewing
   a repertoire.
2. **Calibrated easier opponents and staged lessons.** The current lowest
   Stockfish setting is advertised around 1320 Elo, already strong for a new
   player. Measure actual playing behavior rather than assigning a smaller Elo
   label; add exercises for piece safety, mating patterns and basic endings with
   explicit success criteria.
3. **Organized analysis archives.** Complete saved-run backup and restore now
   work. Add optional study-library links and run labels so a tournament player
   can find a comparison by chapter or preparation session, retaining explicit
   engine sources, limits and missing coverage.
4. **Chess960 after a rules-layer design.** Add only when castling, imports,
   exports, board input and UCI position encoding can be tested together. This
   expands serious-player coverage but is larger than the fixes above.
