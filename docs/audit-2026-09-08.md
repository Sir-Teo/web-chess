## Measured performance improvement

Previously, on a capable desktop with **32 MB Hash**, the planner selected four workers, found each would have only 8 MB, and abandoned the pool. The revised planner selects **two workers with 16 MB each**. The equivalent 48 MB case now supports three workers. Low-memory/mobile safeguards remain in force.

Real Chromium, Stockfish 18 Lite single-thread build, 18 reported logical cores, 33 nonterminal Opera Game positions, depth 18, total Hash 32 MB, fresh workers in ABBA order. No other repository test or benchmark was run concurrently with this recorded repeat.

| Run | Workers | Seconds | Nodes | Scored at requested depth |
| --- | ---: | ---: | ---: | ---: |
| A1 | 1 | 16.951 | 32,979,660 | 33/33 |
| B1 | 2 | 3.864 | 13,035,269 | 33/33 |
| B2 | 2 | 3.923 | 13,035,269 | 33/33 |
| A2 | 1 | 20.956 | 32,979,660 | 33/33 |

Mean: **18.954 s → 3.894 s**, approximately **4.9× faster / 79% less time for this workload**. The serial runs varied materially. This is not a universal two-worker speedup: partitioned transposition-table history also reduced searched nodes by about 60%. Equal depth does not establish equal evaluations, accuracy scores, or playing strength; those were not compared in this benchmark. Existing 64 MB pooled reviews are not newly accelerated by this fix.

Reproduce:

```sh
npm run dev -- --host 127.0.0.1 --port 4324
REVIEW_BENCH_HASH_MB=32 REVIEW_BENCH_WORKERS=2 node scripts/benchmark-review-browser.cjs
```

The benchmark now fails if any target lacks a score or fails to reach the requested depth. [Raw results](qa/2026-09-07/review-32mb-benchmark.json).

Final application entry is **95.58 kB gzip**, versus **94.03 kB** at baseline; React remains 60.35 kB and chess/board 37.31 kB. The ECO table remains a separate lazy chunk. Engine WASM is additional. No dependencies were added.

## Highest-priority remaining defects

### P1 — A library save in another tab can erase newer games

**Reproduction:** Open two fresh browser pages sharing one context; let both load the empty library. Save game A through the first page's storage API. Save game B through the second page's original snapshot. Reload the store: only `From B` remains. Reproduced with actual Chromium IndexedDB, using the application's storage modules rather than a mock.

**Cause:** `useGameLibrary.commit` submits a whole snapshot. `saveToIndexedDb` clears the object store and rewrites that snapshot. There is no cross-tab revision check or merge.

**Recommended fix:** Per-game transactional writes/deletes, conflict handling for simultaneous edits, and change notifications to refresh other tabs. Test concurrent additions, deletes, renames, capacity limits, and fallback storage. This is also a likely performance improvement for large libraries, since a star/rename should not rewrite every PGN. Its latency benefit has not been measured here.

Owners: [storage](../src/engine/gameLibraryStorage.ts), [library hook](../src/hooks/useGameLibrary.ts).

### P1 — The app can export a JSON backup it refuses to import

**Reproduction:** Create 17 valid games, each with a 480,000-character PGN note, below the per-game limit. `createLibraryBackup` produces **8,161,664 characters**. `parseLibraryBackup` returns **zero games**, because its input cap is 8,000,000. Reproduced in Chromium.

**Impact:** A professional annotated library can outgrow backup recovery well before reaching its 500-game capacity. The exporter imposes no matching limit.

**Recommended fix:** A round-trip-safe backup format with bounded streaming or explicit parts, plus an actionable export error until that exists. Simply allowing arbitrarily large JSON on the main thread would exchange a recovery problem for a memory/freeze problem. Test the maximum supported library, Unicode expansion and partial/corrupt backups.

Owner: [library formats](../src/engine/gameLibrary.ts).

### P1 — Study arrows and square annotations are discarded on PGN import

**Reproduction:** Parse `1. e4 { [%cal Ge2e4] [%csl Ge4] My plan } *`. The retained comment is only `My plan`; there are no node fields preserving the arrow/square directives. Reproduced in Chromium.

**Cause:** `humanCommentFromPgnComment` strips all PGN command tags. Some tags, such as evaluations and clocks, are parsed separately; these study annotations are not.

**Recommended fix:** Preserve structured annotation fields and unknown directives independently from generated engine comments. Render known arrows/squares and export all retained data. Verify nested variations and repeated import/export cycles. This enables persistent annotations and a touch annotation tool without losing imported studies.

Owner: [PGN parser/exporter](../src/engine/pgn.ts).

### P2 — Position readings lack sufficient history and engine identity

**Confirmed premise:** These two legal histories produce exactly the same full FEN, including counters:

```text
A: Nf3 Nf6 Ng1 Ng8 Nf3 Nf6 Ng1 Ng8
B: Nf3 Nf6 Nc3 Nc6 Ng1 Ng8 Nb1 Nb8
FEN: rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR w KQkq - 8 5
```

`chess.js.isThreefoldRepetition()` is true for A and false for B. The application's shared evaluation map and review sufficiency lookup are keyed by FEN. The engine request itself carries move history, and its navigation cache includes the request; the application-level map is the separate concern.

**Recommended fix:** Define evaluation identity using node/history context and engine configuration; distinguish imported/cloud readings from current local analysis. A cached high-depth reading should not automatically establish review completeness under a different context or strength configuration. The identity collision was reproduced; an incorrect end-to-end numerical score was not measured here.

Owners: [App evaluation state](../src/App.tsx), [review planner](../src/engine/batchReview.ts), [analysis sufficiency](../src/engine/analysis.ts).

### P2 — Remaining reliability and maintenance concerns

- **Engine Lab has overlapping setting owners.** Hash/MultiPV/WDL can be changed through UCI controls while the next app analysis request supplies the separate app settings. Reconcile those controls or label temporary overrides. Threads now feeds the review budget; that does not unify all other settings.
- **Startup deadlines do not cover every later stalled search/handshake.** The new watchdog ends at readiness. Audit Stop acknowledgments and subsequent thread reconfiguration separately, especially while reviewing or requesting a hint.
- **Runtime asset cache has no entry bound or deploy-generation cleanup.** `public/sw.js` retains a fixed cache name and accumulates successful hashed assets. Test repeated deployments and quota pressure before implementing safe pruning of obsolete generations.
- **Library persistence acknowledgment is optimistic.** The hook updates the UI before the asynchronous write settles. Test storage failure after the initial durability check, not only storage unavailable at boot.
- **Orchestration remains concentrated.** `App.tsx` is 7,826 lines; `App.css` is 5,652. Extract review, recovery and engine-setting controllers behind behavior tests. This is primarily a correctness and maintainability improvement until profiling establishes a rendering benefit.

Run the confirmed format/storage/history probes with:

```sh
node scripts/audit-reproductions-browser.cjs
```

This uses fresh browser data and prints current behavior; it is an audit probe, not a passing regression test. [Recorded output](qa/2026-09-07/audit-reproductions.json).

## UI/UX conclusions

**Keep:** The board dominates Play mode, first-screen actions are useful, Coach defaults to plain language, Pro reveals richer controls, and dialogs are separated from the playfield. Existing keyboard move entry, variation navigation, PV preview and practice flows are valuable. Desktop, 375px mobile and 844×390 landscape passed the browser suite.

**Improved in this pass:** Recovery status is persistent and actionable; it is not a disappearing toast. The Coach guide is collapsed by default and expands inside the analysis panel. It explains why the human-game win-chance model and engine-game WDL model can display very different percentages. Advanced review resource use is visible and adjustable. The oversized import was exercised through a real file input, and the warning appeared correctly.

**Next beginner work:** A truly gentle training opponent or handicap mode, practice by theme, and a guided first review. The current weakest Stockfish Elo target is still demanding for a new player; weakening by Elo plus occasional alternative candidates is not a complete beginner curriculum. Keep its approximate strength labeling honest.

**Next mobile work:** Add a touch mode for arrows/square marks and clearer discovery of the icon-only toolbar. Test long-press conflicts and panel scrolling on real touch hardware; narrow desktop viewports alone do not establish touch usability. The screenshots here include a touch-enabled Chromium context.

**Next accessibility work:** Screen-reader playthroughs of promotion, branch selection, result announcements and the continuously updating analysis panel. Automated names, focus checks and contrast probes do not replace VoiceOver/NVDA testing.

## Research used

- [Stockfish UCI documentation](https://official-stockfish.github.io/docs/stockfish-wiki/UCI-Protocol-and-Stockfish-Commands.html): Threads/Hash configuration, MultiPV's search cost, strength limits, and WDL's engine self-play basis. Decisions: retain MultiPV 1 for review, expose resource budgets, and explain WDL instead of treating it as a player's personal probability.
- [Lichess accuracy explanation](https://lichess.org/page/accuracy): its score-derived winning-chance model and accuracy interpretation informed the Coach guide. Accuracy should not be presented as a direct rating estimate.
- [Stockfish.js](https://github.com/nmrugg/stockfish.js): browser build/profile reference. All four local JS/WASM assets were compared byte-for-byte with the installed package and matched.
- [Lichess stockfish-web](https://github.com/lichess-org/stockfish-web): integration reference; no evidence from this pass justifies replacing the functioning Stockfish.js integration before fixing resource use and provenance.
- [Nibbler](https://github.com/rooklift/nibbler): focused engine-analysis workflow reference. Continuous analysis, candidate exploration and PV inspection already exist here; avoid duplicating them.
- [En Croissant](https://github.com/franciscoBSalgueiro/en-croissant): database/repertoire toolkit reference for prioritizing professional study management beyond engine toggles.
- [Chessground](https://github.com/lichess-org/chessground): board interaction and rendering reference. Its documented small footprint and minimal DOM writes suggest a comparison experiment, not a justified wholesale board rewrite without profiling.

External projects were reviewed as documented workflow/architecture references. Their complete implementations and Stockfish's generated binary internals were not audited.

## Coverage and verification

The audit covered application orchestration, game tree and rule helpers, engine boot/search/review scheduling, evaluation/accuracy logic, PGN/FEN/share paths, library/autosave persistence, cloud/explorer/tablebase hooks, board/dialog/graph controls, responsive/theme styling, assets, service worker, build configuration and workflows. High-risk paths received the detailed reproductions above. This is subsystem-level inspection plus behavioral testing, not a claim to have proved every source line or possible chess position correct.

- Baseline: 103 test files, 1,412 passed / 1 skipped; typecheck, lint and build passed.
- Final code: 103 test files, **1,415 passed / 1 skipped**; typecheck, lint and build passed.
- `npm run audit`: **zero reported vulnerabilities** at the time of this pass.
- Full Chromium UI suite run after each implementation commit. Existing checks include review completion/stability, practice, clocks/takeback, drills, typed moves, hidden-tab search handling, cache reuse, themes, dialogs, mobile layouts and service-worker isolation/offline/range behavior. New checks cover recovery failures, startup silence, worker limits and the Coach guide.
- One intermediate verification caught two `prefer-const` errors, corrected in the final startup commit. One intermediate continuous-analysis browser check timed out while another local build had overlapped the suite; the isolated check and complete rerun passed. Subsequent browser runs were kept separate from builds outside the harness.
- The deployment YAML was parsed and its browser-before-upload ordering checked. GitHub-hosted deployment execution was not run.
- Full real-engine ABBA benchmark and screenshots supplement the deterministic fake-engine suite. Public-service availability is intentionally not required for deterministic regressions.
- Firefox/WebKit, real phones, assistive-technology playthroughs, maximum-size professional databases and full-CDN peak memory remain unverified.

For the next performance pass, measure per-game IndexedDB writes, autosave export/serialization on large variation trees, and main-thread frame cost while live analysis updates. Preserve the existing request debounce, navigation-search cache, lazy ECO loading and shared replay cache; those optimizations are already present.
